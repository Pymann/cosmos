# 114 — Git: pipelines from a repository, runs from its events

Status: decided 2026-11-26.  First slice: git through the **ufo command line**.  ufo as an aiml
package that a pipeline calls directly comes later (§114.7).

## 114.1 Why

Until now a cosmos pipeline came from a file on the server (`from_dir`, doc/spec/111 §111.4) or
from a submission.  A project's build definition does not live in its own repository, and a push
or a pull request starts nothing.  That leaves three gaps:

- the pipeline that builds a commit is not the one **in** that commit;
- a pull request is not built before it is merged;
- the person looking at a commit on GitHub cannot see whether cosmos built it.

The first acceptance case is cosmos building its own pull requests and those of ufo and kontor.

## 114.2 What is configured

```yaml
- config:
    secrets:
      - secret: { name: gh_hook,  file: secrets/github-hook.secret }
      - secret: { name: gh_token, env: COSMOS_GITHUB_TOKEN }
    git:
      webhook_secret: gh_hook       # HMAC of /api/v1/hooks/github (F114-6)
      token: gh_token               # fetch private repositories, post commit statuses
      api_url: "https://api.github.com"   # the default; another for GitHub Enterprise or a test stub
      status: on                    # commit statuses back (F114-11); off = fetch and run only
- catalog:
    from_repo:
      - url: "https://github.com/Pymann/cosmos.git"
        branch: main                # where the CATALOG reads its pipelines from (F114-2)
        path: ci                    # each *.aiml / *.yaml in it is one job, as from_dir
        triggers: [push, pull_request, tag]
```

- **F114-1** `config.git` holds what every repository shares: the webhook secret, the token and
  the API url.  Both secrets are **names** (doc/spec/111 §111.1, F100-10); the values reach no log,
  no answer and no model.  A missing `git:` turns the webhook off (401 for every delivery) and
  leaves `from_repo` readable for public repositories.
- **F114-2** `from_repo` is `from_dir` with a repository instead of a directory.  The catalog
  reads the files at the **head of `branch`** when it is read (plan and apply see the same bytes,
  §111.1), sorted; a job's name is `<repository>-<file name without extension>` (`cosmos-build`),
  so two repositories with a `ci/build.aiml` give two jobs.  `project` comes from the header line
  `# project: <name>` as with `from_dir`.  Removing a file or the whole entry disables its jobs
  (F100-15).
- **F114-3** `triggers` says which events start the job: `push` (a branch moved), `tag` (a tag was
  pushed), `pull_request` (opened, pushed to, reopened).  `kontor` stays allowed beside them.
  Without `triggers` a job from a repository runs by hand only.

## 114.3 Where the repository lives

- **F114-4** cosmosd keeps **one bare mirror per repository** under `<state>/git/<host>/<owner>/
  <name>.git`, made with `ufo init --bare` and `ufo fetch`.  It reads files out of it with
  `ufo cat-file -p <commit>:<path>` and `ufo ls-tree`; nothing is checked out on the server.  The
  ufo binary is `ufo` from `PATH`, or `COSMOS_UFO` — the same rule as every other tool cosmosd
  starts.
- **F114-5** Fetching **does not block the server**.  The catalog's read waits for its fetch (it
  is an operator's request, with a time limit of 120 s, and fails closed like every other catalog
  error).  An event's fetch is started detached and looked at on each tick; the run is created
  when the fetch has finished.  A fetch that fails leaves the event in the log with ufo's message
  and starts nothing.

## 114.4 The webhook

`POST /api/v1/hooks/github` — no bearer token; the signature proves the sender, as with kontor
(§111.6).

- **F114-6** The body is accepted only when `X-Hub-Signature-256` is `sha256=` followed by the
  HMAC-SHA256 of the raw body under `config.git.webhook_secret`.  Anything else is 401 and starts
  nothing.  `X-GitHub-Delivery` is remembered (the last 1000): a delivery GitHub sends again is
  answered 202 and ignored.
- **F114-7** The repository of an event is matched against the `url` of every `from_repo` entry by
  `<host>/<owner>/<name>`, case-insensitive and without `.git` (`clone_url`, `html_url` and
  `ssh_url` all match).  Events of a repository the catalog does not name are answered 202 and
  ignored, with a log line.
- **F114-8** What an event is:

  | `X-GitHub-Event` | condition | trigger | commit | ref |
  |---|---|---|---|---|
  | `push` | `ref` = `refs/heads/*`, not `deleted` | `push` | `after` | the branch |
  | `push` | `ref` = `refs/tags/*`, not `deleted` | `tag` | `after` | the tag |
  | `pull_request` | `action` ∈ opened, synchronize, reopened | `pull_request` | `pull_request.head.sha` | `refs/pull/<n>/head` |
  | `ping` | — | — | — | answered 202 |

  Every other event or action is answered 202 and starts nothing.
- **F114-9** A pull request **from a fork** is not run.  Its pipeline is code from someone who
  cannot push to the repository, and a run executes it on our agents.  The event is logged with
  that reason.  Running such pull requests needs an explicit approval step, which is not part of
  this slice.

## 114.5 A run from an event

- **F114-10** The pipeline of the run is the job's file **at the event's commit**, not at the head
  of `branch`: a pull request that changes `ci/build.aiml` is built by its own `ci/build.aiml`.  A
  commit in which the file does not exist starts no run for that job.  The source is checked
  (`submitter.check`) exactly as a run by hand; a refused source is a log line, not a run.
- **F114-11** The run knows where it comes from through parameters in the namespace `prm`
  (doc/spec/106 F106-19), so a step reads them like any other parameter:

  | function | value |
  |---|---|
  | `${prm.git_url}` | the repository's clone url |
  | `${prm.git_sha}` | the commit |
  | `${prm.git_ref}` | `refs/heads/main`, `refs/tags/v1.0`, `refs/pull/12/head` |
  | `${prm.git_event}` | `push`, `tag`, `pull_request` |
  | `${prm.git_pr}` | the pull request number, `0` otherwise |

  The names `git_*` are reserved: a job parameter of that name is overridden by the event.  They
  are frozen with the run's other parameters (F106-14).  A run by hand from a repository job gets
  the head of `branch` that the catalog read last and `git_event` = `manual`: the catalog
  writes these values into the job's parameters when it applies, so a pipeline that reads them
  also builds by hand and by schedule.
- **F114-12** Where a run came from is kept **beside** the run, in KV `run_git` (run id →
  `GitOrigin`), for the reason marks and layers are (doc/spec/108 F108-2).
- **F114-13** The checkout is the **step's** work, with ufo:

  ```yaml
  - stage: { name: checkout, run: "ufo clone ${prm.git_url} .repo && ufo -C .repo checkout-tree ${prm.git_sha} src" }
  ```

  `checkout-tree` takes a commit and writes its tree into a directory (checked with ufo on
  2026-11-26: a commit that is not the head of any branch checks out).  cosmos gives the step the
  url and the commit, not a working tree: what a checkout means (depth, submodules, which
  directory) belongs to the pipeline.  A **private** repository needs the token
  in the step, and that is the next item, secrets for steps; until then a step can check out
  public repositories only.  The step runs in the agent's sandbox, which sees the host's `/usr`
  (doc/spec/91): `ufo` has to be installed there, or in the step's image, like every other tool a
  step calls.

## 114.6 Commit statuses back

- **F114-14** With `status: on`, cosmos posts a commit status for each run that came from an event
  (`POST <api_url>/repos/<owner>/<name>/statuses/<sha>`), with the context `cosmos/<job name>` and
  the run's page as `target_url`:
  - `pending` when the run is created;
  - `success` or `failure` when it ends (`done` / `failed`);
  - `error` when no run could be made from the commit's pipeline (the source was refused; the
    reason is in cosmosd's log), or the run is gone;
  - a run with a magenta step (doc/spec/113) keeps its state and says so in the description
    (`passed — version mismatch in 1 step`).  A version mismatch never turns a green commit red.
- **F114-15** Posting a status never changes the run.  A refused or unreachable API is a log line
  with the HTTP code; the status is tried again on the next transition and not otherwise.

## 114.7 What this is not, yet

- **ufo as an aiml package in the pipeline syntax** — a step that checks out without a shell
  command, with the commit typed — comes after this slice.  The parameters of F114-11 are what it
  will take.
- **Secrets for steps** (private repositories, publishing) are the next item.
- **Polling** a repository without a webhook, **approval for fork pull requests** and **other
  forges** (GitLab, Gitea) are open.
